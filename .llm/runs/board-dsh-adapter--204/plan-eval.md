## Verdict: **PASS AFTER NARROW FIXES**

The plan is feasible against the installed API. I confirmed the load-bearing claims independently: `ctx.sessionProjections.register({key, stateSchema, init, apply, wire, stateVersion})` and `snapshot(session, keys)` exist as described (`dsh-session-projection/lib/types/index.d.ts:38-80,176-185`); `Session.append` is **synchronous** and returns the logged event (`dsh-session/lib/types/index.d.ts:230`); `ctx.sessions.create()` takes no required arguments and is in-memory, so the no-agent/no-home smoke is genuinely credential-free (`dsh-session/.../index.d.ts:311-336`); tool-todo registers `todos` with last-write-wins on `todo/write` and reset on `turn/start` (`dsh-tool-todo/lib/index.js:63-94`); the pure chain composes — `BoardSnapshot.items` (`packages/board/src/model.ts:180`) feeds `normaliseItems`' `{items:[…]}` envelope (`packages/telemetry/src/items.ts:133-138`), `toRef` carries `milestone`/`isEpic`/`kind` off `source` (`items.ts:99-131`, `packages/board/src/model.ts:16-30`), and `publicTree` rebuilds all four levels while `publicRun` omits `origin` (`packages/telemetry/src/public.ts:157-223`, `:39-73`). GitHub stays one-way. The plan does **not** claim atomicity — the risk register admits the transient two-event cut, which is the honest reading.

Six bounded fixes.

**F1 — the missing-`todos` failure fires after both appends (partial mutation).** D3 says refresh "appends both whole values, verifies both keys are present in the returned dsh snapshot" (plan.md:56), and step 2's last bullet promises to "fail explicitly if the composed `todos` key is absent" (plan.md:130-131). `append` validates JSON-serializability and event type only — it knows nothing about registered projections — so with tool-todo unloaded both events land and *then* refresh throws, leaving a `harness/board-write` in the log that no todo list pairs with. Fix: make it a precondition — check `"todos" in ctx.sessionProjections.snapshot(session, ["todos"]).values` (the key is present-and-`null` before the first write) *before* the first append, and assert the failing case leaves `session.seq` unchanged.

**F2 — `refresh`'s sync/async contract is unspecified.** "Fixed todo-first/rich-commit order" (plan.md:212) does not prevent interleaving; if `refresh` is `async` or awaits between appends, two concurrent refreshes can commit `todo(A), todo(B), board(B), board(A)` and cross-pair the two keys. Since `append`, the pure chain and `snapshot` are all synchronous, the fix is free: state that `refresh` is synchronous end-to-end. Also state that it must not be invoked from a projection change listener — `append` rejects a reentrant append opened inside the publication boundary (`dsh-session/.../index.d.ts:229`).

**F3 — D5's strict Zod schema over `PublicTree` is unproven, unspiked, and its fallback is pre-forbidden.** `stateSchema`/`viewSchema` are `ZodType<S>` from `zod` (4.5.4, single instance — version pin in D6 is correct). This repo compiles with `strict` + `exactOptionalPropertyTypes: true` (`tsconfig.base.json:10-11`), and `BoardItemRef` deliberately uses exact-optional keys (`packages/telemetry/src/model.ts:182-200`, with `items.ts:115-117` naming that setting as load-bearing). Zod's `.optional()` produces `k?: T | undefined`, which is not assignable to `k?: T` under that flag — so `ZodType<PublicTree>` may not typecheck across ~9 nested interfaces. There is **no zod usage anywhere in `packages/*/src`** to draw on, the plan declares "Spikes: None" (plan.md:112-116), and D5 explicitly rejects `z.unknown()` (plan.md:89-91), leaving no stated escape. Fix: either add a bounded spike, or name the fallback now (e.g. a strict object schema wrapped so the declared output type matches exactly) and reframe the gate as behavioural — the schema accepts a real `publicTree(...)` output and rejects an added key — rather than mandating one construction.

**F4 — D6's "package root and `/types` exports" is wrong for tool-todo.** `@deepseek-ai/dsh-tool-todo` publishes only `.`, `./invariant`, `./client`, `./src/*`, `./package.json` — there is no `./types` subpath; the `SessionEventMap`/`SessionProjectionMap` augmentations arrive via the root's `export type * from './types.ts'`. (`dsh-session-projection` *does* export `./types`.) Following D6 literally, guided by research.md's file-path citation, yields an unresolvable import. Fix: name the exact entrypoint per package. Same paragraph: tool-todo's `Config.allowParallelInProgress` is `z.boolean().required()` with no default (`lib/index.js:19`), so the integration test and smoke must pass it explicitly — plan step 3 doesn't say so.

**F5 — adding `sessionProjections` to `inject` silently deactivates `ctx.harnessBoard`.** Plan step 2 adds it unconditionally (plan.md:127). Cordis then withholds the whole service on a bare `Context`, which breaks the existing `harness-board` test that boots `new Context()` with no dsh services (`packages/dsh-app/src/plugins.test.ts:116-125`) — the exact behaviour the subagents/telemetry case at `:100-113` already demonstrates — and couples the pure projector's availability to the registry. The registry docs offer the intended alternative: `ctx.inject(['sessionProjections'], …)` for optional registration (`dsh-session-projection/.../index.d.ts:128-130`). Fix: register optionally so `project()` survives without the registry, or state that the existing test changes and confirm the composed profile provides `sessionProjections`.

**F6 — D4's `bucketOf` input is under-specified (minor).** `bucketOf(item: BoardItem)` reads `item.phase.name`/`.queued` (`packages/board/src/hierarchy.ts:135-144`), but tree and public task nodes carry `BoardItemRef`, whose `phase` is `string | null` (`packages/telemetry/src/model.ts:181`). Todos must be derived from `BoardSnapshot.items`, not from the tree. The compiler forces this, but say it so the "existing projected order" and epic/PR exclusion are read off the same list.

Two smaller notes, no gate change: the `smoke:board-projection` script needs `tsc -b` ahead of `node dist/board-smoke.js` (dsh-app's only build path is the `test` script, `packages/dsh-app/package.json:46`); and `normaliseItems` returns `{ok:false, notes}` on a malformed envelope (`items.ts:147-155`) — the plan never says whether refresh surfaces those notes or fails.

Scope held: no mutation, network, auth, env, home-telemetry, sibling-repo reads, subagents, or unrelated history. Nothing in the plan forks published dsh or adds a dsh edge to `@rickylabs/board` — that boundary stays intact (`packages/board/package.json` has no dsh dependency).
