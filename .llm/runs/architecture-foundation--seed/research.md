## 1. Summary of findings

1. **"Harness" currently names two different systems.** A runtime harness and a process harness.
   They coexist in the same vocabulary and are not the same thing. The product must either
   unify them explicitly or separate them explicitly; it cannot inherit the ambiguity. (§2)
2. **NetScript already contains the entire runtime spine** the product needs — tasks, jobs,
   workers, sagas, triggers, streams, KV persistence with optimistic concurrency, multi-runtime
   execution, and OS-service deployment. Very little needs inventing. (§3)
3. **The doctrine ported across a total stack swap** — Deno/JSR/Aspire to Next.js/React/Sanity/bun —
   with mechanics transferring cleanly and domain knowledge transferring not at all. (§4)
4. **The run-state ownership question is unresolved and load-bearing.** The two live
   implementations disagree, and PR #14 logged the disagreement as accepted drift rather than
   resolving it. Every control-plane question depends on it. (§6)
5. **The competitive middle is empty.** The two nearest products own the surfaces on either
   side of the process substrate and neither owns the substrate. (§7)

## 2. Finding: "harness" is overloaded

Two systems share the name across the evidence base.

| | **Runtime harness** | **Process harness** |
|---|---|---|
| Seen in | `rickylabs/eis-chat` | `autocorner/website` |
| Entry | `netscript.config.ts` → `netscript generate` | `.llm/harness/` doctrine → `use harness` |
| Substrate | Aspire apphost, job registry, plugin loading, codegen | Markdown lifecycle, templates, profiles |
| Primitives | Task, Job, Worker, Saga, Trigger, Stream | Stage, slice, gate, fork, drift, verdict |
| Persists to | Deno KV / Redis / Turso | Files in a run directory |
| Ships as | CLI + supervised workers + native window + MSI | Nothing; it is documentation |
| Failure mode | A daemon dies | A decision is taken silently |

Cited:
- Runtime: `eis-chat/netscript.config.ts` (27 lines — paths, plugins, Aspire appHost); generated
  outputs at `eis-chat/.netscript/generated/plugin-workers/job-registry.ts` and
  `eis-chat/aspire/apphost.mts`, both regenerated by `netscript generate`.
- Process: `website/.llm/harness/{README,WORKFLOW,HELP,INDEX,PRINCIPLES,LESSONS}.md`, plus
  `profiles/` (5) and `templates/` (13).

**Consequence for the product.** The name in the product must be assigned deliberately. The
working position for Stage C is that the product *is* the process harness, *built on* the
runtime harness — matching the brief's own phrasing — but this has not been ratified and is
carried into `plan.md` as a decision, not assumed here.

## 3. Finding: NetScript supplies the runtime spine

At `netscript@f7898dba`. All shapes below are read from source, not from documentation.

### 3.1 Execution primitives

`packages/plugin-workers-core/src/domain/task.ts`:

```ts
type TaskDefinition = {
  id: TaskId;
  name: string;
  type: TaskType; // 'deno' | 'python' | 'shell' | 'dotnet' | 'cmd' | 'powershell' | 'executable'
  entrypoint: string;
  permissions: TaskPermissions; // { net, read, write, env, run, ffi, import? }
  source: TaskSource; // 'local' | 'plugin' | 'remote' | 'inline' | 'shared'
  enabled: boolean;
  topic?: string;
  pluginId?: string;
};
```

Two properties matter disproportionately for this product:

- `type` already spans `powershell` **and** `shell` **and** `executable`. A cross-boundary
  Windows↔WSL supervisor is expressible in the existing model without extension.
- `permissions` is explicit and per-task. A remotely-triggered task from a phone has a
  declarable, auditable blast radius. This is a prerequisite for the control plane, and it
  already exists.

`packages/plugin-workers-core/src/domain/job-definition.ts` adds `attempts`, `maxAttempts`,
`nextRetryTime`, `idempotencyKey`, `correlationId`, and an `ExecutionStatus` of
`pending | queued | running | completed | failed | timeout | cancelled`.

`correlationId` plus `topic` is, structurally, the agent tree the brief asks to see from
orchestrator down to leaf. It does not need to be invented.

### 3.2 State persistence

Rule observed in NetScript doctrine: all long-lived state in KV or SQL; no in-memory state
across restarts. Reserved KV prefixes:

```
['workers','tasks']  ['workers','jobs']  ['workers','idempotency']  ['workers','executions']
['sagas']            ['triggers']
```

Sagas carry `SagaStateEnvelope<TState>` with `metadata.version` and optimistic concurrency via
`SagaStoreWriteOptions.expectedVersion`, plus `transitions[]` and `compensationQueue[]`
(`packages/plugin-sagas-core/src/stores/kv-saga-store.ts`).

**A harness run is a saga.** Stages A→H with gates, an append-only transition record, and
compensation on failure is precisely the saga shape already implemented. Whether the product
should model runs as sagas is a genuine design choice with real consequences, and is carried to
`plan.md` rather than assumed.

### 3.3 Ingress

`TriggerType` = `cron | manual | api | event | retry | queue | plugin`
(`packages/plugin-triggers-core/`). `api` and `manual` cover dashboard-initiated work; `cron`
covers supervision sweeps; `event` covers reacting to agent output.

### 3.4 Distribution and supervision

- Install: `deno install --global --name netscript jsr:@netscript/cli`
  (`packages/cli/bin/netscript.ts`).
- Command groups: `init`, `plugin {add,remove,enable,disable,sync,doctor}`, `service {add,generate}`,
  `db {add,migrate,seed}`, `deploy {build,up,down,status,logs}`, `ui {add,init}`
  (`packages/cli/src/public/features/root/public-command-tree.ts`).
- `deploy up` targets include **bare-metal**, Deno Deploy, Kubernetes, Azure, Cloud Run;
  bare-metal installs an OS service via an `OsServicePort` abstraction — Servy on Windows,
  systemd on Linux (`packages/cli/src/kernel/adapters/deploy/`).

This is the direct, deterministic answer to the daily-workflow complaint about rescuing dead
daemons from a second desktop client: a supervised OS service does not need an agent to
restart it.

### 3.5 Runtime reach beyond Deno

31 packages publish to JSR and are installable on Node and Bun via `npx jsr add` / `bunx jsr add`.
Documented adapter fallbacks: Redis replaces Deno KV, and an in-memory scheduler replaces
`Deno.cron`. **Not verified by execution in this run** — see §5, F-2.

### 3.6 Extension model

Plugins expose contribution *ports*; the host wires them at runtime. Each plugin is split into
a `*-core` contract package with no runtime dependencies and a `plugins/*` implementation that
binds the contract to Hono, KV, and Aspire. Fitness gates (`deno task arch:check`,
`deps:check`) enforce the split.

This is the mechanism by which the product would support Claude Code, Codex, opencode and
Copilot as interchangeable agent transports: one `AgentTransportPort`, four implementations.

## 4. Finding: the doctrine ported across a total stack swap

`autocorner/website@d77bcaf` runs Next.js 16 / React 19 / Sanity 5 / bun. It shares no runtime
with NetScript. It nevertheless carries a working harness.

Layered layout observed:

```
.llm/harness/      stable doctrine — WORKFLOW, PRINCIPLES, HELP, INDEX, LESSONS
  profiles/        5 domain profiles (app, content, integration, docs, knowledge-base)
  templates/       13 artifact templates
.llm/tmp/run/<id>/ ephemeral run artifacts, gitignored
.llm/audit/        foundational analysis
.claude/           10-doc knowledge base, task-indexed
.agents/skills/    8 behavioural skills
AGENTS.md CLAUDE.md  entry points
```

What transferred unchanged: run-ID naming, lifecycle phases, stable/ephemeral split, template
shapes, principle set, knowledge-base structure. What required complete rewriting: all
knowledge-base content, all profile checklists, all skill content.

**This asymmetry is the product seam.** Mechanics are shippable; knowledge must be scaffolded
and authored per project. A distribution that ships only mechanics is correct; one that ships
example knowledge as if it were reusable would be actively harmful.

Observed cost to bootstrap the pattern into a new repository, per the port: roughly 150 KB of
structure, of which the mechanics are copy-and-adapt and the knowledge is 4–6 hours of authoring.
**Unverified estimate, single data point** — recorded as such, see §5.

## 6. The unresolved contradiction: who owns run state

The two live implementations disagree, and the disagreement is documented rather than settled.

- `website/.llm/harness/` treats runs as **ephemeral**: `.llm/tmp/run/<id>/`, gitignored,
  auto-cleaned after durable learnings are promoted into the knowledge base. Stated rationale:
  the harness stays small and runs do not pollute git history.
- `autocorner/website` PR #14 used **durable** runs: `.llm/runs/plan-convex-platform--seed/`,
  20 files, committed and reviewed as a pull request. The PR body records this as accepted drift
  D-4/D-5, noting the website harness's `.llm/tmp/` is "explicitly non-archival".

The same harness, in the same repository, in the same week, took both positions.

For a documentation-only harness this is a preference. For a product with a live dashboard,
a background daemon and mobile steering, it is the **central data-communication decision**,
because these all follow from it:

- what the dashboard reads, and whether it can read it without a git checkout
- whether a phone can observe a run on a machine it cannot clone
- what happens to run state when a branch is deleted or a worktree is discarded
- whether two machines can advance the same run
- what "resume" means, and whether it survives a lost daemon

Three candidate positions, stated here without preference, for Stage C to develop and Stage E
to lock:

1. **Git-authoritative.** The run directory is the truth; the daemon indexes it; the dashboard
   reads the index. Review is native. Multi-machine is hard. Mobile requires a server-side clone.
2. **Daemon-authoritative.** KV is the truth; git receives a projection at stage boundaries.
   Live observation is trivial. Review becomes a publishing step, and the record is only as
   durable as the daemon's storage.
3. **Split by lifecycle.** In-flight state is daemon-owned; stage-committed artifacts are
   git-owned; the gate transition is the synchronisation point. More moving parts; matches how
   both implementations actually behaved.

This is filed as the first entry of the decision register when Stage E opens. It is not
decided here.

## 7. External leg (started, incomplete)

Retrieved 2026-08-14. Held to the citation bar: vendor pages are cited for *intent*, not for
*behaviour*.

**t3.codes** — open-source control interface for coding agents by the Ping.gg team.
Multi-vendor (Codex, Claude Code, Cursor, opencode, Grok), bring-your-own-key, web + Electron +
native mobile, git integration, per-project session threads, `npx t3` to start a local server,
remote control over LAN / Tailscale / tunnel. Source: `github.com/pingdotgg/t3code`; overview
via `betterstack.com/community/guides/ai/t3-code/`.

Relevance: this is the closest existing implementation of the *shell* the brief describes — CLI
install, local server, mobile client, remote steering. It manages **sessions**. It carries no
opinion about the work performed inside them: no stages, no gates, no citation bar, no drift
register, no owner forks.

**Linear** — building agents as first-class team members, contextually grounded in roadmap,
issues and codebase, with an orchestration layer coordinating human-in-the-loop touchpoints.
Source: `linear.app/agents`, `linear.app/plan`.

Relevance: owns **intent** — initiatives, projects, milestones. Agents are participants in a
board. The unit of record is an issue, not a run, and there is no artifact contract for how a
decision was reached.

**The gap.** t3.codes owns the session surface. Linear owns the intent surface. The process
substrate between them — how work is staged, evidenced, contested, gated and made reviewable —
is owned by neither. That substrate is what this repository has already proven across three
codebases.

**Not yet covered by the external leg**, and required before Stage C closes: Conductor, Vibe
Kanban, Sculptor, OpenHands, Devin's orchestration surface, Cursor background agents, GitHub's
own Copilot coding-agent task model, and the AGENTS.md / MCP standardisation trajectory.
