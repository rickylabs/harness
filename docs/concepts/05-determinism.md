# Determinism

The agents are stochastic. The layer around them is not, and that asymmetry is the point.

If both the worker and the scaffolding produce different results from the same inputs, a bad outcome
has no cause you can find. You cannot tell whether the model was having a bad day, the policy
changed, or a generated file drifted three weeks ago — and every debugging session becomes an
argument about what probably happened.

So: **one source of nondeterminism, and it is the model.** Everything this repository owns is a pure
function of its inputs, and where that cannot be true, the deviation is reported rather than absorbed.

## The failure mode being defended against

Not the wrong answer. The quiet one.

`dsh-board`'s default lifecycle once listed six phases — `backlog`, `ready`, `in-progress`,
`blocked`, `in-review`, `changes-requested` — that `dsh-forge` has never stamped on anything. Nothing
failed. `phaseOf` returned `null` for every correctly labelled item, the progress count called them
all invisible, and **a board that had just been filled in reported itself empty.** The board
package's own tests stayed green the whole time, because each test passed its own lifecycle in
rather than using the default.

That is the shape of the bug this whole chapter is about. It does not go red. It goes silent, and
the silence looks exactly like a quiet week.

## Generate, commit, compare

The pattern, wherever a file could be derived from something else:

1. One place owns the fact, in code.
2. The file is generated from it and committed, so a reader can see it without running anything.
3. A test regenerates and compares **byte for byte**. A difference is a failure, not a diff to
   eyeball.

Live instances:

| File | Owner | How drift surfaces |
| --- | --- | --- |
| [`packages/dsh-app/cordis.patch.yml`](../../packages/dsh-app/cordis.patch.yml) | `src/bundle.ts` — rows as typed data | byte-compare in the package's suite |
| [`packages/dsh-app/dump-config.golden.yml`](../../packages/dsh-app/dump-config.golden.yml) | the composed profile itself | re-blessed on purpose: `pnpm run golden:bless` |
| [`.claude/skills/board-process/SKILL.md`](../../.claude/skills/board-process/SKILL.md) | the taxonomy installed in the repo | regenerated by `pnpm run skill:install` |
| [`.github/labels.yml`](../../.github/labels.yml) | the epics and areas in this repository | `dsh-forge labels eject`, then reviewed as a diff |

The golden snapshot deserves its own note, because it is the one that looks like cheating. Blessing
is a *command a human runs*, and the re-blessed file lands in a pull request as a visible diff. The
snapshot does not assert the output is correct — it asserts that a change to the output was somebody's
decision.

Ejection works the same way in the other direction: `labels.yml` is derived from the repository's
own epics rather than hand-maintained, but it is committed and reviewed, so the taxonomy is both
generated *and* readable without a network call.

## Invariants that live between packages

Some facts are true of the workspace and of no single package in it, so they are checked by scripts
the build runs before anything else — `check:graph`, `check:lifecycle`, `check:publish`.

The lifecycle check is the one from the story above. Neither package could catch it: `board` must not
depend on `forge`, because a projector that imports its own installer is no longer projecting
anything. So the invariant is asserted from outside both, where it is actually true.

The graph check exists for a similar reason. `pnpm -r run build` exits 0 with a missing TypeScript
project reference, because pnpm builds from the manifest graph and TypeScript resolves through the
package export — so a reference graph that is merely *correct* is not one that is *enforced*, and the
difference only appears the day someone adds a dependency and forgets the reference.

And the publish check guards the one operation here that a revert cannot undo: an npm version is
immutable, so every mistake it catches would otherwise be permanent and public.

## Decisions are replayable

`dsh-coordinator` records the decisions it makes, and `replay` re-runs a journal against the current
code and compares. A decision that comes back different from identical inputs is reported as
nondeterminism — not as a change of plan.

This is what makes "why was this blocked?" a question with an answer. Each rejection carries a stable
rule id rather than a sentence to parse, and one of those ids exists purely so the record stays
honest: `not-preferred` marks a candidate that was **legal and simply ranked lower**. Without it, a
roster with three viable evaluators and a roster with one produce identical records — and *"there was
no alternative"* is exactly the claim a reader most needs to be able to check.

The same discipline runs through the outputs generally: exit codes are a documented contract per
binary, anomalies have named kinds, and every projection is a pure function of what was fetched.
Prose is for humans; the machine-readable part never depends on reading it.

## The honest limit

The guarantee is only as wide as the checks. Where a generated file is committed without a
comparison running in CI, what holds it true is a convention — someone remembering to regenerate —
and conventions decay silently, which is the failure this page opened with.

Documentation was the largest such gap, which is why the docs lane treats it as an engineering
problem rather than a writing one: the CLI reference is generated from the CLIs and byte-compared
([#143](https://github.com/rickylabs/harness/issues/143)), and links are checked in CI
([#147](https://github.com/rickylabs/harness/issues/147)). The rule those issues serve is the one
stated on the [docs index](../README.md#the-rule-these-docs-are-held-to):

> Every document either states facts it owns, or is generated from the code that owns them.
